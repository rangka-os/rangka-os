# 0013: Money and currency

Status: proposed (3 Nov 2026) · Owner: rangka-os (stream S8a) · Consumers: rangka-apps S8 (`invoicing`, `payments`, `currency`), S3 print, S0 web app

## Context
Pilot A invoices in IDR or USD, with the rate set per document and IDR amounts for reporting
(spec `2026-11-03-first-pilots-design.md`, decision 4). Today's `currency` field type is IDR only and passes
through `float64` in the kernel. The program plan fixes: IDR amounts are integers (whole rupiah); foreign
amounts are decimal strings with an ISO code; never float; money is never decided by an LLM.

## Decision

### 1. Field type `money`
```yaml
fields:
  - {name: currency, type: link, to: currency, default: "'IDR'"}
  - {name: rate, type: float, label: {id: Kurs, en: Rate}}
  - {name: total, type: money, currency_field: currency, compute: "sum(items.map(i, i.amount))"}
```
- The currency field in the example is a `link` to the `currency` module's model, whose record names are the
  ISO codes. It is not a `select`, because select option values must be lower case (`^[a-z0-9_]+$`) and so cannot
  hold ISO codes. A `data` field works too.
- `currency_field` (required): the field holding the ISO 4217 code. It must be a `select`, `data` or `link` field
  of the same model; on a child model it may instead be a field of the parent document (every model that has a
  `table` of it). The child's own field is tried first. The validator accepts `select`, but select option values
  must be lower case and cannot be ISO codes, so use `link` or `data`.
- `rate_field` (optional, default `rate`): IDR per one unit of the foreign currency, a `float`, `currency` or `int`
  field of the document. For a model that is not a child, it resolves on the model itself. For a child model it
  resolves on the parent document(s) only, never on the child: every visible model with a `table` of the child
  must have it, and the first one that lacks it (sorted by model name) is reported. A child's own field with that
  name is ignored, because lines such as `sales_invoice_item` use `rate` for the unit price. Required whenever the
  model has a `money` field.
- Existing `currency` stays IDR only and unchanged.

### 2. Storage
- `<field>`: `numeric(20,4)`. Values outside ±9,999,999,999,999,999.9999 are refused.
- `<field>_idr`: `bigint`, the IDR twin, generated by the kernel for every `money` field. It is a read-only field of
  type `currency` in the registry (so lists, dashboards, kanban sums, print `rupiah` and change-set risk treat it as
  rupiah), visible to CEL, views and dashboards. A model may not declare a field named `<field>_idr` itself.
- Generated twins carry `money_of: <field>` in `/api/v1/meta`. Clients that write a model back (Console, Rangka AI
  change sets) must drop fields with `money_of` first.
- Money fields added by a company overlay (`site/custom/<model>.rk`) get their twins at runtime, but the validator
  runs no money checks on overlay fields in v0. Overlay views cannot reference the twin of an overlay money field
  in v0 (the validator reports `unknown_field`); use it from expressions only.
- The kernel reads money columns as text (`"<field>"::text`), so no value passes through `float64`
  (independent of the pgx swap in contract 0005).

### 3. Values and rounding
- An empty currency means IDR (the site's base currency; only IDR is supported as base). Other codes must be three
  upper-case letters.
- **IDR documents stay whole rupiah.** When the currency is IDR, computed money values are rounded to whole rupiah
  as they are computed (so later computes see the rounded value), and an entered value with a fraction is refused
  (`bad_value`, "Rupiah tidak memakai desimal").
- Foreign-currency values keep up to 4 decimals. Input with more than 4 decimals is refused, not rounded. Apps
  round to cents themselves with `round(x, 2)`.
- **Twin:** `<field>_idr = round(<field> × rate)` to whole rupiah, **half away from zero** (Postgres `round()` on
  numeric, and Indonesian invoicing practice). For IDR the rate is 1, whatever the rate field says.
- A foreign-currency document without a positive rate fails save (`missing_rate`,
  "Kurs wajib diisi untuk mata uang USD"). The twin is never silently 0.
- **A header's twin comes from the header's own amount**, not from the sum of the line twins:
  `total_idr = round(sum(lines.amount) × rate)`. Line twins are each rounded and may not add up to the header
  twin (the difference is at most half a rupiah per line); reports of document totals use the header twin.
- The rate field is read through its shortest decimal form, exact for rates with up to 15 significant digits.
- A row of a row reads the rate from the top-level document, whatever its depth. (The validator still resolves
  `rate_field` on the direct parent in v0, so an intermediate row needs a `rate` field of an allowed type too; the
  kernel ignores it.)
- A `default` that yields a fraction in an IDR document is refused at save like an entered fraction (only computes
  are rounded).
- **Twins inside computes.** A compute may read `<field>_idr` (its own record's, or a row's through
  `items.map(i, i.amount_idr)`). Twins are settled before the record's computes and again after each one, and a
  compute reading a twin runs after the money field (and a computed currency or rate) it depends on, so it sees the
  twin of the current amount and rate, on create and on update.
- A decimal stored into a non-money field is converted, never silently 0: into `float`, `percent` or `currency` as
  the nearest double, into `int` or `rating` rounded half away from zero, into text as its canonical string.

### 4. CEL
- A `money` field evaluates to a decimal value (`decimal` in error messages).
- `+ - *` between decimals, and between a decimal and an int or double, give a decimal; `*` keeps full precision of
  both operands, then rounds the result half away from zero to 4 decimals. `/` does the same; division by zero is
  an error. Doubles enter through their shortest decimal form (`0.11` is exactly 0.11).
- `== != < <= > >=` compare decimals with decimals, ints and doubles exactly.
- `sum(list)` of decimals (or decimals mixed with ints) is an exact decimal.
- `round(x)` rounds a decimal to a whole number, `round(x, n)` to `n` decimals (0–4), half away from zero; both stay
  decimals. `round(x, n)` on doubles also rounds half away from zero. `round(x)` on doubles is unchanged: it keeps
  the prototype's JavaScript rounding (`Math.round`, half up), so `round(-2.5)` on a double is `-2`, while
  `round(-2.5)` on a decimal is `-3`.
- `int(x)` of a decimal truncates toward zero, like `int(x)` of a double (`int(-2.7)` is `-2`); `double(x)` of a
  decimal is the nearest double. Storing a decimal into an `int` field rounds instead (§3).
- When cel-go replaces the in-tree evaluator (contract 0005 §1), the decimal type and these overloads move with it;
  the semantics here are the contract.

### 5. API JSON shape (REST, MCP, SSE, change sets, fixtures)
```json
{"currency": "USD", "rate": 15873.5, "total": "1250.5", "total_idr": 19849812}
```
- A `money` value is a JSON **string**: plain decimal, no exponent, no trailing zeros after the point
  (`"1250.5"`, `"1250000"`, `"0"`). The twin is a JSON integer.
- Input accepts a string (preferred) or a JSON number (read through its shortest decimal form). Send large amounts
  as strings: a JSON number above about 15 significant digits has already lost precision when it is decoded.
  Clients may send `<field>_idr`; it is ignored and recomputed.
- Input errors are Bahasa Indonesia with the field label: "<label> maksimal 4 angka desimal" (more than 4
  decimals or no number), "<label> terlalu besar" (outside numeric(20,4)).

### 6. Validator (Go and `rangka_validate.py`, identical reports)
- Schema: `money` in the field type enum; `currency_field` and `rate_field` keys; `type: money` requires
  `currency_field` (the same jsonschema "required property" error as `link` without `to`).
- `bad_currency_field` (error): `currency_field` names no field of the model (or its parents), or a field that is
  not `select`, `data` or `link`.
- `missing_rate_field` (error): no `rate_field` (default `rate`) of type `float`, `currency` or `int` on the
  document.
- `twin_clash` (error): the model declares `<field>_idr` for a `money` field `<field>`.
- `<field>_idr` counts as a field of type `currency` for expressions, views, kanban sums and dashboards; a
  `money` field itself is not summable in kanban or dashboards (use the twin).

### 7. Schema version
The additions are additive and live in `schema/0.5/model.json` (S5 bootstrapped 0.5 as a copy of 0.4);
`schema/0.4/` is unchanged.

## Consequences
- S8 (rangka-apps) builds `invoicing` and `payments` on `money` + `rate`, with dashboards and AR aging on `*_idr`.
  A USD payment against an IDR invoice converts at the payment's rate and rounds to whole rupiah (Review Focus) by
  allocating `amount_idr`.
- S3 print's `money` helper formats a decimal string with its code (`USD 1,250.50`); `rupiah` formats the twin.
- S0 renders money fields from the string value plus the currency field, and must not do money arithmetic in
  floating point (the server stays authoritative).
- Not in scope: exchange-rate tables or automatic rates (the `currency` module may add a rate lookup that fills
  `rate` as a default), a base currency other than IDR, realised FX gain/loss.
