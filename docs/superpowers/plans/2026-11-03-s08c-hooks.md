# S8c Business Hooks Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement in the kernel the named hooks that the rangka-apps modules of `jasa_proyek` and `fnb_cabang` call: receivables, payables, payment allocation, document conversions, and stock with moving-average cost, recipes and the negative-stock exception.

**Architecture:** Go functions registered in `registerBuiltinHooks` (`kernel/internal/engine/hooks.go`) like `crm.convert_lead`. Each runs inside the document's transaction through `HookCtx`. Hooks are generic: they only assume the model and field names fixed in the program plan and in rangka-apps `docs/superpowers/plans/2026-11-03-s08-modules.md` ("Model reference"). A hook whose models are not installed returns `{"message": "… not installed"}` like `crm.mark_won`.

**Tech Stack:** Go 1.24, PostgreSQL 16, the kernel's engine/store packages.

**Spec:** rangka-os `docs/superpowers/specs/2026-11-03-first-pilots-design.md`; program plan Review Focus; rangka-apps branch `claude/pilot-s08-modules-2ae378`: `docs/superpowers/plans/2026-11-03-s08-modules.md` (Model reference, Tasks 3–9) and `docs/kernel-hooks.md` (invoicing section; the semantics below win where they differ).

## Global Constraints
- IDR amounts are integers (whole rupiah). Every computed money value is rounded half away from zero to a whole rupiah exactly once, where this plan says so. No float for money: compute values in int64 or exact decimal (quantities and factors may be float64, and a value is `round(qty × cost)`).
- Money, stock and document numbers are never decided by an LLM; nothing here consults one.
- A hook error rolls back the whole submit/cancel. Refusals are `409` `StatusError` with a code from this plan and an Indonesian message.
- Hooks may write `read_only` fields of submitted documents (e.g. `paid_amount`, `system_qty`, `cogs`). Add one engine path for that (e.g. `HookCtx.SetSubmitted(model, name, fields)` that refuses non-read-only fields) instead of loosening `update`.
- Concurrency: lock rows a hook reads to decide (`select … for update` via a store helper) for invoices/bills being allocated and `stock_balance` rows.
- `make -C kernel test` stays green; new tests use a self-contained catalogue under `kernel/internal/engine/testdata/pilot/` (0.4 layout: one dir per unit with `app.rk` + `models/`), copied from the rangka-apps branch's model files, trimmed to the fields the hooks use, plus a minimal site. Do not read the rangka-apps checkout from tests.
- Separate PR from S8b. Do not touch the loader or schemas.

## Hooks (names are the contract; list them all in the PR description)

### Receivables and payables
- `ledger.post_receivable` (sales_invoice on_submit): `customer.outstanding += amount_due`. Also refuses `409 dp_over_deducted` when the sum of `dp_deduction` of submitted invoices with the same `dp_invoice` (this one included) exceeds that DP invoice's `dpp_base`, and `409 retention_billed` when another submitted invoice has the same `retention_of`.
- `invoicing.reverse_receivable` (sales_invoice on_cancel): refuses `409 has_payments` if `paid_amount > 0`, and `409 has_dependents` if a submitted invoice names it as `dp_invoice` or `retention_of`; else `customer.outstanding -= amount_due`.
- `procurement.post_payable` (vendor_bill on_submit): `vendor.outstanding += amount_due`. `procurement.reverse_payable` (on_cancel): the same refusal for `paid_amount > 0`; else subtract.

### Payments
- `payments.allocate` (payment on_submit): for each allocation row, by `idx`: target = `sales_invoice` (direction receive) or `vendor_bill` (pay); lock it; it must be submitted (`409 not_submitted`), belong to the payment's customer/vendor (`409 wrong_party`), and satisfy `amount + withheld <= target.outstanding` against the **stored** value (`409 over_allocation`, "Alokasi melebihi sisa tagihan <name>"). Then `target.paid_amount += amount + withheld` (outstanding recomputes), and party `outstanding -= amount + withheld`. Also refuse when the sum of the rows' `amount` exceeds `payment.amount` (`409 over_payment`). Allocation rows (`amount`, `withheld`) and `payment.amount` are always IDR: a foreign payment converts once at the header (contract 0013 money twin), so the hook does not convert and `applied_idr = amount`. Also refuse `409 negative_allocation` when a row has `amount <= 0` or `withheld < 0`, and `409 pph23_already_deducted` when a row has `withheld > 0` against a `sales_invoice` whose stored `pph23_applies` is true. Two rows on the same invoice are checked cumulatively: the invoice is locked once and each row, in idx order, is checked against the outstanding left by the earlier rows. Write `applied_idr` onto each allocation row (read-only int field; add it to the trimmed test model, and the rangka-apps module adds it too).
- `payments.unallocate` (payment on_cancel): subtract each row's `applied_idr` (+ `withheld`) from the target's `paid_amount` and add it back to the party's `outstanding`. It is the exact inverse.

### Document conversions (actions; return `{"open": {"model", "name"}, "message"}`)
- `quotation.revise` (quotation action `new_revision`, submitted and outcome open): cancel the quotation and amend it (engine Amend) so the new draft carries `revision = old + 1`, `outcome = open`; return the new draft.
- `orders.from_quotation` (quotation action `make_order`, submitted and outcome accepted): reuse an existing draft `customer_order` with `quotation = <q>` if one exists; else create one with customer, quotation and lines (item, description, qty, uom, rate); `po_number` is left for the user (required, so the draft is created with `po_number: ""`. If create refuses empty required fields, set it to the quotation's `rfq_ref` or `"-"`; decide and document).
- `invoicing.from_order` (customer_order action `make_invoice`): as in rangka-apps docs/kernel-hooks.md (reuse a draft; remainder per item; `409 nothing_to_invoice`). On invoice submit, `ledger.post_receivable` also adds the invoice's `subtotal` to `customer_order.invoiced_amount` when `customer_order` is set (the reverse on cancel).
- `procurement.make_po` (purchase_request action): draft purchase_order with the request's lines (item, qty, uom, packing, rate = est_rate), `purchase_request` and `outlet`; vendor from the action call body `{vendor}` (required: `422 vendor_required` "Vendor wajib diisi" when missing; never left empty or guessed); set the request's `state = ordered`.
- `procurement.receive` (purchase_order action `receive`, submitted): draft goods_receipt with vendor, outlet, purchase_order and the not-yet-received remainder per line (qty, uom, packing, rate). On goods_receipt submit, `stock.post_moves` adds the received qty to the PO lines' `received_qty` and sets `received_pct`.

### Stock (`stock.post_moves` on_submit, `stock.reverse_moves` on_cancel) for goods_receipt, stock_transfer, stock_count, stock_adjustment, outlet_sales
- Unit of measure: every quantity is converted into the item's `stock_uom` through the line's `stock_qty` (computed by the model). For lines without `stock_qty` (outlet_sales lines, recipe lines, count lines), the quantity is already in stock uom.
- Balance row: `stock_balance` per (outlet, item), created on first move, locked for update.
- Incoming (`in_qty > 0` at `unit_cost`): `in_value = round(in_qty × unit_cost)`; if `bal_qty + in_qty > 0` then `avg = round((bal_value + in_value) / (bal_qty + in_qty))`, else avg unchanged (still the previous avg, or unit_cost when none). `bal_qty += in_qty`, `bal_value = round(bal_qty × avg)` when bal_qty > 0 else `bal_value += in_value`.
- Outgoing (`out_qty > 0`): `value = round(out_qty × avg)` (avg = current; when no avg yet use `item.standard_cost`, else 0); `bal_qty -= out_qty`; `bal_value -= value`. **Never refuse**: negative balance is allowed. When `bal_qty < 0` after the move, the move has `negative = true`.
- One `stock_move` per (document line, item affected) with posting_date (document date), outlet, item, signed qty, unit_cost, signed value, balance_qty, balance_value, avg_cost, negative, voucher_type (model), voucher (name), reason.
- Per document:
  - goods_receipt: + `stock_qty` at `unit_cost` into `outlet`, reason receipt; update PO `received_qty`/`received_pct`.
  - stock_transfer: − from `from_outlet` at its avg (transfer_out); + into `to_outlet` at the same unit cost (transfer_in).
  - stock_count: for each line, read the balance → write `system_qty` and `difference = counted_qty − system_qty` onto the line; post the difference (incoming at the current avg when positive, outgoing when negative), reason count.
  - stock_adjustment: − `stock_qty` at avg, reason from the header (`waste|damage|expired|other` → move reason `waste` for waste, else `adjustment`).
  - outlet_sales: for each line, the active `recipe` with `product = item` (most recently modified if several): each recipe_line consumes `material`: `line.qty × recipe_line.qty / yield_qty`. No recipe: if the item's kind is good, material or product, consume the item itself; services are skipped. reason sale. The line's `cogs` = sum of the values it consumed; header `cogs_total` = sum. Also refuses `409 duplicate_sales` when another submitted outlet_sales has the same outlet, date and source `form` (a Moka import is protected by S7's key check instead).
- Negative-stock exception: every move with `negative = true` creates (or updates the open one for the same outlet+item) an exception visible to head office. Implement it as data: the move's `negative` flag + `stock_balance.negative` (a compute in the model), and emit the normal `stock_move.created` event so the module's flow `stock_negative_alert` notifies. Confirm the flow sees `event.negative`; if events carry no record fields, document the payload shape the flow must use.
- `stock.reverse_moves`: for each stock_move of the voucher, a `reversal` move with the opposite qty and value (incoming/outgoing rules as above, at the original move's unit cost for the reversed quantity); revert received_qty, line cogs and count lines' system_qty are left as they were (history). Cancelling twice cannot happen (cancel is once per document).
