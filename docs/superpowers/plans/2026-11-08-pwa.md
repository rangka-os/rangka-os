# Rangka app as a PWA: analysis and plan (8 Nov 2026)

> **Status (8 Nov 2026, branch `feat/pwa-shell`).** The analysis below was first written against an older branch.
> Since then `main` has gained a few things that change the plan:
>
> - A phone bottom tab bar (Beranda / Setujui / Cari / Menu, design direction E).
> - `outbox.js` with `Idempotency-Key` writes and a per-user "data terakhir" read cache for work screens (contract 0030).
> - Juragan branding.
>
> **Phase 1 as built:**
>
> - Manifest and Sendi icons.
> - A network-first `sw.js`: no stale-cache risk, so no per-release version is needed. Google Fonts are cached at
>   runtime instead of self-hosting four families.
> - `pwa.js`: registration, update toast, install entry, iOS hint and status-bar colour.
> - Kernel `no-cache` headers.
> - The offline strip, and a "Belum ada koneksi" start that retries by itself.
> - Unit tests, plus the live scenario `test_pwa_installable_and_offline`.
>
> **Dropped from phase 1:**
>
> - The new tab bar. It already exists, and its tabs stay as design direction E chose them.
> - The self-hosted font.
>
> **Phase 2 and 3 are partly in place.** Contract 0030 already brings idempotent writes and the per-user read cache to
> work screens. What is left is reading the last-seen desk pages (dashboards, lists, records) offline, so the whole app
> opens without a connection.

Scope: the end-user app `web/app/` served by the kernel at `/app/`. The Console (`web/console/`) is an operator tool
and stays a plain web page for now (see "Not in scope").

## 1. Where we are

| Area | Today | PWA-relevant gap |
| --- | --- | --- |
| Responsive layout | Works from 400px to desktop. `viewport-fit=cover`, safe-area padding on `.ap-shell`, breakpoints at 860 / 640 / 600px, off-canvas sidebar, `test_app.py --width 400` | Good base. No `display-mode: standalone` rules (top inset, no browser back button) |
| Manifest | None in `web/app/` | Not installable. `website/public/` already has `site.webmanifest`, `icon-192.png`, `icon-512.png`, `maskable-512.png`, `apple-touch-icon.png` (docs site only) |
| Service worker | None anywhere in `web/` | No offline start, no install prompt on Android, no push |
| Theme colour | Light/dark via `data-theme` + `localStorage` `rk-app-theme` | No `<meta name="theme-color">`, so the status bar is not Ink/Kapur |
| Assets | No build step: React UMD vendored in `web/app/vendor/`, 13 plain `<script>` files, design-system `bundle.js/css`, `../canvas/*` | Easy to precache (small, fixed list). One external request: Google Fonts (Bricolage Grotesque) breaks offline start |
| Kernel static serving | `http.FileServer(http.Dir(WebDir))` in `kernel/internal/api/server.go` `static()`; release binaries extract `web/` from `internal/bundle` | No cache headers, no version string. A service worker needs `sw.js` served `no-cache` and a cache name that changes per release |
| Routing | Hash routes (`#/r/<model>/<name>`) | Ideal: every navigation is `/app/index.html`, so one cached shell covers all routes |
| Auth | Cookie session (`HttpOnly`, `SameSite=Lax`), 401 opens an in-app sign-in dialog; OIDC under `/oauth/` | SW must never intercept `/auth/`, `/oauth/`, `/mcp`. Cookies work in an installed PWA (same origin) |
| Data | All reads/writes `fetch` to `/api/v1` with `credentials: "include"`. No IndexedDB, no offline flag | Nothing readable offline. Multi-org (contract 0010) means any cache must be keyed by user + org |
| Realtime | Kernel has `GET /api/v1/events` (SSE); the app does not use it | Fine for v1; useful later to refresh cached data and approvals badge |
| Writes | No `Idempotency-Key` on record create/update, no `If-Match`/version check on update | Blocks safe offline writes (retries could double a record; a queued edit could overwrite a newer one) |
| HTTPS | Juragan deploy has Caddy (TLS); Rangka Cloud is HTTPS | Service workers need HTTPS or `localhost`. A self-hosted kernel on `http://192.168.x.x` gets the manifest but no SW |

**Answer to "is it a PWA already?": no.** It is responsive, but it has no manifest, no service worker and no offline
behaviour. The good news: the no-build, hash-routed, single-origin app is about the easiest shape there is to turn
into a PWA. Phase 1 below is a few days of work and touches only `rangka-os`.

## 2. Principles

1. **Money and stock stay online in the browser.** Offline selling, printing and stock moves belong to `rangka-edge`
   (contracts 0003 / 0006), which has a durable queue, idempotency keys and device access. The PWA never becomes a
   second, weaker offline POS.
2. **Never cache API data in the HTTP cache / Cache Storage.** Shared devices and multi-org make that a data leak.
   Offline data, when we add it, lives in IndexedDB keyed by `user + org`, and sign-out or org switch wipes it.
3. **The shell must always update.** A stale cached `form.js` against a newer kernel is worse than no PWA. Network
   first for HTML, versioned cache, visible "Versi baru tersedia" prompt.
4. **No build step introduced.** A hand-written `sw.js` (~150 lines) fits the current no-bundler app; no Workbox,
   no `vite-plugin-pwa`.
5. **Graceful without SW.** Plain HTTP self-hosting still works exactly as today.

## 3. Phases

### Phase 1: Installable app shell (rangka-os only, no contract needed)

Goal: "Tambahkan ke layar utama" on Android/iOS/desktop, opens full screen with Rangka colours, starts offline into a
clear "Kamu sedang offline" screen instead of the browser's dinosaur.

Web (`web/app/`):
- `manifest.webmanifest`: `name` "Rangka", `short_name` "Rangka", `id` "/app/", `start_url` "/app/#/",
  `scope` "/app/", `display` "standalone", `background_color` `#FFFFFF`, `theme_color` `#FFFFFF` (dark: `#1A1715`,
  so the status bar blends into the white top bar; mockups: https://claude.ai/artifact/WDEN31UvoNvPyK4hdKqBbq), `lang` "id",
  icons 192 / 512 / maskable-512 (copy from `website/public/`, Sendi mark), `shortcuts`: Persetujuan (`#/approvals`),
  Beranda. Screenshots (narrow + wide) for the richer Android install sheet.
- `index.html`: `<link rel="manifest">`, `<meta name="theme-color">` twice with `media="(prefers-color-scheme: …)"`,
  `apple-touch-icon`, `apple-mobile-web-app-capable`, `apple-mobile-web-app-title`. `shell.js` updates `theme-color`
  when the user picks a theme in the account menu.
- Self-host Bricolage Grotesque (woff2 in `web/app/fonts/` or the design system) and drop the Google Fonts link, so
  the first offline start renders correctly.
- `sw.js` (scope `/app/`):
  - precache the shell: `index.html`, `tokens.css`, `vendor/*`, the 13 app scripts, `../design-system/bundle.{js,css}`,
    `../canvas/canvas.{js,css}`, fonts, icons, `offline.html`.
  - navigations: network first, fall back to cached `index.html` (the app then shows an offline banner when
    `/api/v1/meta` fails with `code: "network"`).
  - static assets: stale-while-revalidate inside the versioned cache.
  - pass through untouched: `/api/`, `/auth/`, `/oauth/`, `/mcp`, `/.well-known/`, attachments, print views, any
    non-GET.
  - `activate` deletes old caches; no `skipWaiting()` by default. The page shows a toast "Versi baru tersedia ·
    Muat ulang" and posts `SKIP_WAITING` on click.
- `shell.js`: register the SW (only when `"serviceWorker" in navigator` and not inside the Rangka Cloud frame),
  offline/online banner from `navigator.onLine` + network errors, the update toast, and on sign-out
  `caches`/IndexedDB cleanup hook (empty in phase 1, used in phase 2). Standalone CSS: `@media (display-mode:
  standalone)` for top safe area and an in-app back button on record pages (no browser back in iOS standalone).
- Android install prompt: capture `beforeinstallprompt`, show "Pasang aplikasi" in the account menu (and the
  bottom sheet in mockup 3, at most once per device, after the second visit). iOS has no prompt: a one-time hint
  ("Bagikan → Tambahkan ke Layar Utama") on iPhone Safari, dismissible.
- **Bottom tab bar on phones** (mockups 2 and 4), replacing the hamburger at ≤ 640px; tablets and desktop keep the
  top nav + sidebar unchanged.
  - Four tabs: **Beranda** (the first dashboard), **Data** (the first model entry of the sidebar, i.e. the first
    `model:` item in `nav.side`, else the first app menu model), **Persetujuan** (only when the approvals feature is
    on; count badge from `GET /api/v1/approvals`, the same number later feeds the app badge), **Lainnya** (opens
    today's full sidebar menu as a bottom sheet, incl. org switcher, theme, Ubah, sign out). Without approvals: three
    tabs. Hidden during Ubah and preview mode, where the existing bars take the bottom of the screen.
  - Active tab: Kapur pill behind a Bata icon, label 12px semibold; inactive stone `--muted`. Touch target ≥ 52px
    tall, `padding-bottom: env(safe-area-inset-bottom)`. Page content gets bottom padding so the last row is not
    hidden; toasts sit above the bar.
  - Built in `shell.js` as `ap-tabbar` (CSS in `index.html`) so Phase 1 stays inside `web/app`; once it settles, move
    it into the design system as `BottomNav` (the design-system artifact is the source, `web/design-system/bundle.js`
    is a copy).
  - Phone top bar slims down with it: org switcher (name + outlet) on the left, search ("Cari atau tanya Raka") and
    the avatar on the right; the app switcher and help icons move into Lainnya.
  - No schema change now. Owner-pinned tabs (`layout.rk` `nav.bottom`) come later through a contract, since
    `schema/0.4/layout.json` would change.
  - Tests: `node --test` for the tab-picking rule (dashboard / first model / approvals on or off); `test_app.py
    --width 400` checks the bar, the badge, Lainnya opening the menu, and that the hamburger is gone; `--width 1280`
    checks the bar is absent.

Kernel (`kernel/internal/api/server.go` `static()`):
- `sw.js` and `manifest.webmanifest`: `Cache-Control: no-cache`, correct MIME (`application/manifest+json`).
- Cache version: the SW cache name must change every release. Two options; recommend (a):
  (a) `scripts/bundle-assets.sh` writes `web/app/version.json` (hash of all precached files) and `sw.js` reads it
      at install; in dev the file is absent and the SW uses `dev-<timestamp>` with network first for everything.
  (b) the kernel serves `sw.js` as a small template with the build version injected.
- Optional: `Cache-Control: public, max-age=…` on `vendor/` and fonts.

Tests:
- `node --test`: pure parts (URL classification "cache / pass through", update-toast state).
- `test_app.py`: Playwright with `service_workers="allow"`: manifest is valid and linked, SW activates, reload with
  the network offline shows the shell + offline banner, `/api/` responses are never in Cache Storage, sign-out
  leaves no API data, a changed `version.json` triggers the update toast.
- Lighthouse PWA installability check in CI (or `npx @lhci/cli` locally) against `make run-demo`.

Docs: README section "Install as an app", note that HTTPS is required (Caddy in `deploy/juragan` already does it),
docs site page.

Effort: 5–7 days (3–5 for the PWA plumbing, 2 for the bottom tab bar and slimmer phone top bar). Risk: low.

### Phase 2: Read what you last saw, offline (rangka-os only)

Goal: on a weak connection (very common for UMKM staff on mobile data), the dashboard, lists and records you opened
recently still show, clearly marked "Data terakhir dilihat 27 Okt 2026 14:05", read only.

- `api.js`: a thin read-through cache in IndexedDB (`rk-cache-<user>-<org>`), only for GET `meta`, `dashboards/*`,
  `r/<model>` list pages already viewed, `r/<model>/<name>`. Size cap (e.g. 500 records / 20 MB) with LRU eviction.
- On `code: "network"` the views render cached data with a stale banner; all write buttons disabled with the reason
  "Butuh koneksi".
- Wipe on sign-out, org switch, 401, and when `/auth/me` returns a different user.
- Respect permissions: we only ever store what the server already returned to this user; nothing is prefetched.
- Use the existing SSE `GET /api/v1/events` when online to invalidate cached records (bonus: live lists).
- Decision for the owner: whether some models must never be cached (payroll, health records). Proposal: a per-model
  opt-out in the app (`meta.models[m].offline === false` once the schema allows it, see phase 3), default on.

Effort: 1–1.5 weeks. Risk: medium (cache invalidation, shared devices).

### Phase 3: Offline drafts for non-money records (cross-repo, needs a contract)

Goal: a sales rep logs a lead, an activity, a visit note or a timesheet line with no signal; it syncs later.
Explicitly not: invoices, payments, stock entries, submit, cancel, approve.

Needs contract **0018 offline drafts** in `rangka-os/docs/contracts/` because it changes the schema and kernel API:
- Schema 0.4 model key `offline: drafts | read | none` (default `read`). Validator rejects `drafts` on models with
  money or stock flags.
- Kernel: `Idempotency-Key` header on `POST /api/v1/r/<model>` and `PATCH …/<name>` (store key → result for 7 days);
  optimistic concurrency on update (`If-Match` with the record's `modified`, `409 conflict` with the current
  record).
- Client: outbox in IndexedDB, temporary names (`~offline-1`), replay in order when online (Background Sync where
  available, else on `online` event / app start), conflict screen "Data ini sudah diubah orang lain: pakai punyaku /
  pakai yang terbaru". Only `docstatus 0` creates/edits; submit always online.
- Ties in with the AI rule: nothing queued offline can apply a change set.

Effort: 2–3 weeks incl. contract review. Risk: medium-high; only worth it if pilot interviews show field staff
working without signal.

### Phase 4: Native-feeling extras

- **Web Push** for approvals ("Faktur INV-0012 menunggu persetujuanmu"): a `webpush` driver under `notify` in
  `system.rk` (VAPID keys in secrets, contract 0017), `push_subscriptions` table, subscribe from the account menu.
  iOS supports it only for installed PWAs (iOS 16.4+), so phase 1 install matters. Needs a small contract (driver
  config shape).
- **App badge** (`navigator.setAppBadge`) with the pending approvals count.
- **Share target**: share a CSV into Rangka → import wizard; share a photo/PDF → attach to a record.
- **Per-company manifest** on Rangka Cloud: kernel-served `manifest.webmanifest` with the org's name and theme
  colour from `theme.rk` (needs `crossorigin="use-credentials"` on the manifest link).
- File handling / protocol handlers: later, only if asked.

## 4. Not in scope (and why)

- **Offline POS in the browser.** That is `rangka-edge` (0003/0006): durable queue, device connectors, price
  snapshot rules. A browser tab can be killed, its storage evicted under pressure (iOS evicts after ~7 days without
  use), and it cannot talk to a cash drawer reliably.
- **Console as a PWA.** Operators use a desktop; it also loads React from cdnjs. Revisit after phase 1 by reusing
  the same `sw.js` with a different precache list.
- **Tauri desktop.** Separate track; the same bundle works there without the SW.

## 5. Risks and decisions

| Risk / question | Proposal |
| --- | --- |
| Stale shell after a kernel upgrade | Network-first HTML, versioned cache from `bundle-assets.sh`, update toast; kernel sends `no-cache` on `sw.js` |
| Data leak on shared phones | No API data in Cache Storage; IndexedDB keyed by user+org, wiped on sign-out/switch/401 |
| Self-host over plain HTTP | Works as a website, no SW. Docs push HTTPS (Caddy). Show nothing broken, just no install |
| Rangka Cloud iframe embedding | Don't register the SW when `window.top !== window`; Cloud can link to `/app/` for install |
| iOS limits (no install prompt, storage eviction, push only when installed) | One-time install hint; phase 2 treats IndexedDB as a cache, never as the source of truth |
| The 27 Oct 2026 decision says React + Vite; the app is actually UMD without a build | Keep the hand-written SW; if a Vite build lands later, swap to a generated precache list then |
| Who decides which models may be cached / drafted offline | Owner via model `offline:` key (phase 3), default `read` |

## 6. Suggested order

1. Phase 1 in one branch/worktree (`pwa-shell`): manifest + icons + theme-color + self-hosted font, `sw.js`,
   kernel headers + version file, update toast, offline banner, bottom tab bar + phone top bar, tests, docs.
2. Pilot it on the Juragan deploy (HTTPS) with 2–3 phones (Android Chrome, iPhone Safari).
3. Phase 2 if pilots report weak signal; phase 4 push alongside approvals usage.
4. Write contract 0018 only when an interview shows a real offline-drafts need.
