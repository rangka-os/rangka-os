# 0052 Ruang coba: a sandbox org with demo data

Status: proposed (14 Nov 2026) · Owner of the change: rangka-os (this contract, kernel) · Affects: rangka-cloud (demo
pack pool, offer after build, console page), rangka-ai (`sandbox` on a turn, demo pack generation), web app (switcher,
banner), design system (`sandbox` token) · Amends: 0026 §3 (whole-org delete of a sandbox), 0028 §1 (limits skip
sandbox orgs) · Builds on: 0009, 0010, 0020, 0033, 0046 §4, 0047, 0051

## Context

- **Owner decision (Dede, 14 Nov 2026).**
  - After Raka builds a business, the owner should be able to try the flow with demo data before entering real data.
  - The demo data must not be generated by an LLM for each owner. It comes from a **pool kept in rangka-cloud**.
  - The demo lives in a **separate org**, and the owner switches between it and the real business.
- **What exists.**
  - The studio's hosting form has "Pakai data contoh" (`SampleData`, rangka-cloud `internal/provision`). It copies the
    studio's `fixtures/start.rk` into the real org: one outlet and the owner, nothing to try a flow with.
  - rangka-apps `examples/fixtures/demo-*` hold synthetic data per business kind (`demo-fnb`, `demo-kursus`,
    `demo-langganan`, `demo-manpower`, …), used by `rangka seed` and `npm create`.
  - 0010 §3 already switches orgs: `GET /auth/me` lists `orgs`, `POST /auth/org` switches a browser session and sets
    cookie `rk_org`, and the web app shows an org switcher. Row-level security keys every model table by `org_id`
    (0010 §4).
  - Number series are counted per org (0009, `rk_number_series`).
- **Why demo data must not share the real org.**
  - Ledgers are append-only (0026): a demo invoice, once submitted, cannot be removed.
  - Demo documents would also take the real series' numbers, and the first tax and stock reports would carry them.
  - 0028 counts limits over every org of the tenant, so a demo org would use up the plan.

## Decision

### 1. The sandbox org

- `rk_orgs` gains `sandbox boolean not null default false`. A site has at most one sandbox org.
  - Its id is `<real org id>-coba`, its name "Ruang coba", and its code `COBA`, so its numbers read `INV/COBA/…`.
- **Who manages it:** a person with role `owner` in the real org, never a token with `ai: true` (0020 §4).
  - `POST /api/v1/sandbox {fixtures}` creates it, makes the caller its owner, and seeds it (§4). If it exists:
    409 `sandbox_exists`.
  - `POST /api/v1/sandbox/reset {fixtures?}` deletes its rows and seeds it again.
  - `DELETE /api/v1/sandbox` deletes the org and every row of it.
  - CLI: `rangka sandbox create|reset|delete --fixtures <dir>` for self-hosted sites.
- **Whole-org delete.** Deleting or resetting a sandbox removes its rows from append-only models as well. This is the
  only exception to 0026 §3, and it applies to sandbox orgs only. Audit entries `sandbox.created`, `sandbox.reset`
  and `sandbox.deleted` go to the real org.
- **Expiry.** A sandbox with no request for 30 days is deleted by the scheduler. A banner shows the date from day 27.

### 2. What runs differently in a sandbox

| Area | In a sandbox org |
| --- | --- |
| Connectors (0002, 0033) | Actions are not sent. The job ends `simulated`, with the mapped request in the job log, so the owner sees what would have gone out. Triggers from outside are not routed to it. |
| Edge (0003) | Device jobs of the sandbox are not sent to Edge. They end `simulated`. |
| Notify (WhatsApp, SMTP, push) and outbound webhooks | Not sent; `simulated`. |
| Flows, rules, scheduler, numbering, dashboards | Run as usual, so the flow can really be tried. |
| Change sets | `propose`, `approve` and `apply` from a session or token whose current org is a sandbox are refused with 409 `sandbox_readonly_meta`. Metadata belongs to the site and is shared with the real org, so a change made "in the sandbox" would change the real business. |
| Plan limits (0028) | The sandbox's outlets, users, records, storage and API calls are not counted. A user who is a member only of the sandbox does not count as a user. AI credits count as usual. |
| Backups (0005 §2) | The sandbox is left out, and a restore never recreates it. |
| Memory and learning (0047, 0051) | Nothing from a sandbox becomes an episode, an outcome, business memory, shared memory or a fingerprint. |

### 3. Switching

- 0010 §3 applies unchanged, with these additions:
  - `GET /auth/me` `orgs[]` and `org` gain `sandbox: true|false`.
  - `POST /auth/login` ignores an `rk_org` cookie that names a sandbox org and signs in to the user's first
    non-sandbox membership. A member whose only membership is the sandbox signs in there (staff in training).
    Entering the sandbox is always a deliberate switch.
- **Staff in training.** The owner may add members to the sandbox only, through the member API (0043) with the sandbox
  as the org. They never see the real org.
- **Web app** (S0 shell):
  - the switcher names the two orgs "Usaha asli" and "Ruang coba";
  - in the sandbox, a fixed banner above the page reads "Kamu sedang di ruang coba. Data di sini contoh, tidak ada
    yang terkirim." with the button "Pindah ke usaha asli";
  - the header uses the new design token `sandbox` (a warm amber, not danger red);
  - switching reloads the page, so no screen keeps records of the other org.
- **Raka.** The relay (0020) and Cloud console turns carry `sandbox: true` when the current org is a sandbox.
  - Raka then says the data is demo data and proposes no change set.
  - When the owner asks for a change, Raka answers: "Pindah ke usaha asli dulu ya kalau mau mengubah sistemnya."

### 4. Demo data: a pool in rangka-cloud, no LLM per owner

- **Packs.** The pool is `rangka-cloud/internal/demo/packs/<pack>/`:
  - `pack.rk`: `{name, business_kinds: [...], modules: [...], version}`;
  - fixture files in the `rangka seed` format (model → rows);
  - `flavour.rk`: placeholder lists (product or service names, price bands, outlet and staff names), every name
    fictional ("Contoh" style, as in `examples/fixtures`).

  The first packs are copied from rangka-apps `examples/fixtures/demo-*`.
- **Choosing and filling** (Cloud, plain templating, no LLM):
  1. Pick the pack whose `business_kinds` matches the project and whose `modules` cover most of the site's modules.
  2. Fill the placeholders. Product and service names the owner gave in the interview (map settings and `seed`
     values, 0046) come first, then `flavour.rk`.
  3. Drop rows of models the site does not have.
  4. Send the resulting fixture directory to `POST /api/v1/sandbox`.
- **Company models.** No pack can know a business's `x_` models. The kernel fills each one with 8 rows from a
  generator that uses no LLM, seeded by the sandbox org id so a reset gives the same rows:
  - text: `Contoh <label> <n>`;
  - numbers and money: small round values within `min`/`max` when set;
  - dates: within the last 30 days;
  - options: in turn;
  - links: existing sandbox records of the target model;
  - required fields always filled.

  Raka-drafted company models are never submittable and never stock models (0033 §1), so the generator never posts.
- **Drift guard.** On every bump of the bundled catalogue, rangka-cloud CI validates and seeds every pack against it
  in a throwaway Postgres. Any failure blocks the bump until the pack is fixed.
- **New packs** come through 0051:
  1. Cloud counts sandbox requests from businesses whose kind has no pack.
  2. Once a kind has at least 3 such requests, Cloud files a `raka-candidate` issue of kind `demo_pack` on rangka-cloud.
  3. After a person adds `raka-build`, rangka-ai `POST /v1/demo-pack` generates the pack once, in a batch.
  4. `raka[bot]` opens the pull request to `internal/demo/packs/**` (0051 §2).

  This is the only LLM cost of demo data: once per business kind, never per owner.

### 5. When the owner is offered it

- **After the build.** When the build of an accepted offer finishes (0046 §4), Cloud posts a scripted message, not an
  LLM turn: "Sistemmu sudah jadi. Mau coba alurnya dulu pakai data contoh? Data usahamu tetap kosong dan bersih." It
  has the action "Isi data contoh". Pressing it runs §4 and opens the app in the sandbox.
- **Console.** The business page shows the sandbox state (since when, expiry) with "Isi data contoh" or "Buka ruang
  coba", "Reset data contoh" and "Hapus ruang coba".
- **Studio.** The hosting form's "Pakai data contoh" checkbox is removed: the real org always starts with `start.rk`
  only.

## Contract changes

**rangka-os (kernel)**
- `rk_orgs.sandbox`, the sandbox endpoints and CLI (§1), the whole-org delete exception, the 30-day expiry job.
- Send-time `simulated` for connectors, Edge, notify and webhooks (§2).
- `sandbox_readonly_meta` in change-set propose, approve and apply (§2).
- Limit counting skips sandbox orgs (§2, amends 0028 §1). Backups skip them.
- `/auth/me` `sandbox` and the login rule (§3).
- The company-model generator (§4).
- Relay field `sandbox` (§3).
- Tests: a sandbox invoice never takes a number of the real series; a sandbox connector action is never sent; a change
  set from a sandbox session is refused; login with a sandbox cookie lands in the real org.

**Web app and design system**
- Switcher labels, the banner, the `sandbox` token (light and dark), reload on switch (§3).

**rangka-cloud**
- `internal/demo/packs` with the first packs from `examples/fixtures`, the picker and templating (§4), and the CI drift
  guard.
- The scripted offer after the build, the console controls, and removing the studio checkbox (§5).
- The `demo_pack` candidate count and issue (§4, through 0051).
- Console turns carry `sandbox` (§3).
- Episodes, memory and fingerprints skip sandbox orgs (§2).

**rangka-ai**
- Request field `sandbox` on `/v1/turn` and the relay: no change-set tools, plus the sentence of §3.
- `POST /v1/demo-pack`: a business kind, its modules and the catalogue in, pack files out. Batch only; Cloud calls it
  after `raka-build`.
